## Context

当前实现是单文件 Cloudflare Worker + D1，webhook 同步处理并以 HTTP 状态码表达结果：200 表示处理完毕，500 请求 Telegram 重投。这个模型本身可行，但目前几处状态转换不是原子的，且 Telegram 错误只被粗分为「话题相关」与「其他」，导致重复处理、消息丢失和映射被错误清空同时存在。动机与缺陷清单见 `proposal.md`；行为契约见本变更的 `specs/`。

约束：

- D1 是 SQLite，支持条件 `UPDATE ... WHERE` 与 `RETURNING`，但没有跨请求的应用级锁，也不提供跨语句事务边界的可靠回滚（Worker 可能在任意语句之间被终止）。
- Worker 可能在任意时刻被平台终止，且同一 update 可能被多个 isolate 并发处理。
- 项目要求保持 Dashboard 粘贴单文件部署，不引入运行时依赖。
- `tg()` 的重试不可假定 Telegram API 幂等：`createForumTopic`、`forwardMessage`、`copyMessage` 重试都会产生真实副作用。

## Goals / Non-Goals

**Goals:**

- 用一组统一的原子原语（claim + 租约、fencing token、条件更新）替代当前分散的时间戳占位与无条件写入。
- 建立单一的 Telegram 错误分类函数，让所有调用方基于同一语义决定重试、重建还是终止。
- 在不改变部署方式的前提下，把正则安全从「黑名单拒绝」改为「白名单解析」。
- 让冒烟测试能够确定性地复现并发、重投与迟到响应，而不是依赖时间竞争。

**Non-Goals:**

- 不引入 Durable Objects、Queues 或外部协调服务。当前规模用 D1 条件更新即可满足，引入新组件会改变部署模型。
- 不追求端到端 exactly-once。Telegram webhook 没有提供实现它的原语；目标是「副作用至多一次，消息至少送达一次或明确失败」。
- 不重写管理面板交互或数据模型的其余部分。
- 不追溯清算此前因缺陷被误标记为已验证的存量用户。

## Decisions

### 1. update 处理采用 claim + 租约 + 终态三段式

将 `processed_updates` 从「布尔已处理标记」升级为带状态与租约的记录：

```text
update_id TEXT PRIMARY KEY
status    TEXT     -- 'processing' | 'done'
lease_until INTEGER
claim_token TEXT
ts        INTEGER
```

处理流程：

```text
1. INSERT OR IGNORE (update_id, 'processing', now+LEASE, token)
2. UPDATE ... SET claim_token=?, lease_until=?
     WHERE update_id=? AND (status='processing' AND lease_until < now)
   -- 用于接管过期租约
3. 只有持有 claim_token 的请求执行副作用
4. 成功后 UPDATE ... SET status='done' WHERE update_id=? AND claim_token=?
```

- `status='done'` 的 update 直接返回 200，满足幂等要求。
- `status='processing'` 且租约未过期表示另一个请求正在处理：返回 500 交由重投，而不是并行执行副作用。
- 租约过期允许接管，因此 Worker 崩溃不会让消息永久卡死。

**为什么不是「处理前直接写 processed」**：那样 Worker 在写入后崩溃会使消息永久丢失，把重复问题换成了更严重的丢失问题。

**为什么不是 Durable Objects**：单对象串行化确实更简单，但会改变部署模型（需要 wrangler 配置与迁移），违反单文件约束。D1 的条件更新足以表达 claim。

**残留风险**：claim 成功后、副作用完成前崩溃，重投仍可能重复已发生的部分副作用。这是 webhook 模型的固有边界，规格因此要求的是「至多一次副作用」在正常路径成立，而非绝对保证。

### 2. 限流额度与 update 身份绑定

限流键从 `rl:<uid>` 改为对「该 update 是否已被计量」的判断：首次 claim 成功时计量一次，重投复用同一 `update_id` 时不再计量。

实现上把限流决策结果记录在 update 的 claim 记录里（例如 `rl_decision` 字段），重投时直接读取，而不是重新 `bumpBucket()`。

**替代方案**：给限流桶加更长窗口。被否决——它只是降低概率，不能消除「重投被限流吞掉」这一类丢失。

### 3. 话题所有权使用 fencing token 而非时间戳

`users` 表增加 `topic_claim_token`。创建流程：

```sql
-- 取得占位
UPDATE users SET topic_claim_ts=?, topic_claim_token=?
 WHERE user_id=? AND topic_id IS NULL
   AND (topic_claim_ts IS NULL OR topic_claim_ts < ?)

-- 写回结果时校验所有权
UPDATE users SET topic_id=?, topic_claim_ts=NULL, topic_claim_token=NULL
 WHERE user_id=? AND topic_claim_token=? AND topic_id IS NULL
```

若第二条影响 0 行，说明占位已被接管：本次创建出的话题是孤儿，记录日志，不覆盖现有映射。

清除失效映射同样条件化：

```sql
UPDATE users SET topic_id=NULL, card_msg_id=NULL
 WHERE user_id=? AND topic_id=?
```

这样针对旧话题的迟到错误无法清除新映射。黑名单共享话题采用同构方案，释放占位时也必须校验 token。

**孤儿话题的处理**：检测到写回失败时，尝试删除刚创建的话题；删除失败仅记录日志，不影响主流程——孤儿话题是可见的运维问题，不是数据损坏。

### 4. 单一 Telegram 错误分类函数

引入统一分类，取代目前散落的正则判断与 `tgQuiet()` 的 `null` 折叠：

| 分类 | 触发条件 | 调用方行为 |
|---|---|---|
| `topic_gone` | thread not found / TOPIC_DELETED | 条件清映射，请求重投 |
| `topic_closed` | TOPIC_CLOSED | 尝试重开；成功则重投，失败按其分类处理 |
| `permanent` | 其他 4xx（含 403 用户停用） | 终止处理，给出可见提示，返回 200 |
| `transient` | 429、5xx、网络异常 | 保持状态不变，请求重投 |

关键点是 `tgQuiet()` 不再用于需要分类的调用（尤其 `reopenForumTopic`）：它把权限失败与限流都变成 `null`，这正是当前误清映射的根因。需要分类的调用改用会抛出带分类信息错误的形式。

管理员回复路径按同一表格处理：`permanent` 时在话题内提示并结束，`transient` 时抛 `RetryLater`。

**重投带来的重复风险**：管理员回复重投可能重复发送。因缓解手段是 §1 的 claim 机制——同一 update 的重投在 claim 层被约束，只有真正未完成的处理才会重放。

### 5. 正则改为解析式安全子集

自行实现一个小型解析器，把 `re:` 模式解析为受限 AST，再编译为 `RegExp`：

- 接受：字面字符、转义序列（`\d` `\w` `\s` `\.` 等）、字符类 `[...]`、锚点 `^ $`、以及**只作用于单个字符或字符类**的 `*` `+` `?` `{m,n}`。
- 拒绝：分组（`(...)`、`(?:...)`）、反向引用、后行断言、作用于分组的量词、嵌套量词。
- 解析器自身按字符扫描并正确处理转义，因此 `\)` 不会被误认为结构字符——这是当前字符串黑名单被绕过的直接原因。

在这个子集下，模式没有可交替的分支，也不存在作用于分组的量词，因此排除了 `(a|aa)+` 这类因分支组合而爆炸的形态。

但**单字符量词链本身仍会指数回溯**：`a?a?a?…aⁿ$` 是经典的 `(a?)ⁿaⁿ` 形态，实测在 512 字符文本上量词数 20 时耗时 642ms、24 时 12.8 秒。因此安全子集之外必须保留量词总数上限（把 `?` 计入，这正是旧实现漏掉的一项），实测取值见实现中的常量注释。

三道防线的分工：解析子集排除分组/交替类爆炸，量词总数上限排除单字符量词链爆炸，文本与模式长度上限限制剩余的多项式规模。

**替代方案对比**：

| 方案 | 安全性 | 部署影响 | 结论 |
|---|---|---|---|
| 继续扩充黑名单 | 低，语法面无法穷举 | 无 | 否决，已两次被绕过 |
| 仅字面关键词 | 最高 | 无 | 否决，移除既有能力 |
| RE2 / WASM | 高 | 需要构建产物 | 否决，破坏单文件部署 |
| 解析式安全子集 | 高，且可解释 | 无 | 采用 |

被拒条目在面板标示为未生效，避免管理员误以为规则仍在保护。

### 6. 编辑消息复用统一准入管线

把 `handlePrivate` 中的准入检查（屏蔽 → 限流 → 验证状态 → 关键词 → 类型过滤）提取为共享函数，`handleEditedMessage` 调用同一函数。编辑通过检查后才发送编辑提示。

这既修复 `/reset` 后的绕过，也消除了「新增一条策略要改两处」的结构性隐患。

### 7. 配置写入改为 CAS

`config` 表增加 `version`。列表与开关的写入统一走：

```sql
UPDATE config SET value=?, version=version+1
 WHERE key=? AND version=?
```

影响 0 行表示并发冲突：重新读取、重放本次意图（追加或删除指定条目）、有限次重试；仍失败则提示管理员操作未生效。

自动回复与问答题目本就带 `id`，删除按 id 定位。屏蔽词是裸字符串，**按值定位删除**（在 CAS 重读后的列表中找到该字符串并只移除一处），不改存储结构。

**为什么不改成带 id 的对象数组**：那会与回滚要求直接冲突。旧版代码把列表元素直接传给 `matchKeyword`，收到对象会退化成 `[object Object]` 参与匹配，等于全部屏蔽词失效。按值定位不改结构、无需迁移，同样消除了基于索引删除误删他项的问题。

**残留边界**：列表中存在两条完全相同的屏蔽词时，两次删除会各移除一条，语义上与管理员预期一致；不存在的值则视为已被他人删除，放弃写入并提示未生效。

### 8. 欢迎语按纯文本发送

存储保持原样，发送前对文本与 caption 统一转义后再使用 HTML 发送方式（等价于纯文本呈现）。`{name}` 同样转义后替换。媒体发送失败时改为发送转义后的 caption 或通用欢迎文案，绝不回退为发送内部 JSON。

### 9. 测试改造：真实重投与确定性并发

- 新增 `sendRawUpdate(env, update)`，直接投递调用方构造的完整 update 对象，`update_id` 与 `message_id` 由测试固定。
- 现有 `webhook()` 保留用于「不同消息」场景，但重投场景一律改用 `sendRawUpdate`。
- 故障注入扩展为可编程钩子：按方法、按调用序号返回指定错误码，并支持「延迟到某个信号后才返回」，用于构造迟到响应与占位接管。
- 并发用 `Promise.all` 配合上述可控延迟，而不是依赖真实时序。

## Risks / Trade-offs

- **claim 记录写入失败会阻塞消息处理** → 租约到期后自动可接管；`claim` 失败时返回 500 而不是放行，宁可重投也不放弃幂等保证。
- **claim 后崩溃仍可能重复部分副作用** → 租约窗口取值需覆盖正常处理时长（含 `tg()` 重试上限），减少误接管；这一残留风险在规格中被显式界定为可接受。
- **迁移期新旧记录格式并存** → schema 迁移使用 `ALTER TABLE ... ADD COLUMN` 幂等添加，缺失字段按「已完成」或「无占位」解释，保证旧数据不被误判为处理中。
- **安全子集拒绝既有正则** → 面板标示未生效条目，并在变更说明中列出受影响写法；管理员可改写为子集内等价形式。
- **CAS 重试可能在高并发下反复失败** → 限定重试次数并向管理员明确反馈失败，而不是静默丢弃或无限重试。
- **管理员回复改为可重投后可能重复送达** → 依赖 §1 claim 收敛；实现顺序上必须先完成 claim 机制，再改管理员回复路径，否则会引入新的重复。
- **改动面广，单次合并风险高** → 任务按依赖分阶段拆分，每阶段独立可测、可回滚。

## Migration Plan

1. 幂等 schema 迁移：为 `processed_updates`、`users`、`config` 补充新列；已存在的 `processed_updates` 行视为 `status='done'`。
2. 先落地 claim/租约与错误分类这两项基础设施，其余修复依赖它们。
3. 屏蔽词结构迁移：读取时若发现裸字符串条目，补齐稳定 id 后写回。
4. 逐阶段部署，每阶段先跑全量冒烟测试。
5. 回滚：粘贴回上一版本 `worker.js` 即可；新增列对旧代码是未知列但不影响其 `SELECT *` 与写入路径，旧代码会忽略它们。屏蔽词结构迁移需保持旧代码可读，因此迁移后条目同时保留原始字符串形式。

## Open Questions
