# topic-relay 增量规格

## MODIFIED Requirements

### Requirement: Update 幂等处理

对同一 `update_id`，系统 MUST 至多产生一次外部可见副作用（转发、复制、发送提示、创建话题、表情回应）；Telegram 因超时或失败重投同一 update 时 MUST NOT 重复转发消息。

幂等判定 MUST 是原子的：系统 MUST 在执行任何副作用之前以单一原子操作取得该 `update_id` 的处理权，未取得处理权的并发请求 MUST NOT 执行副作用。处理权 MUST 带有租约：持有者进程崩溃或超时后，该 update MUST 可被后续投递重新接管，MUST NOT 因取得处理权而被永久判定为已完成。

#### Scenario: 重投的 update 不重复转发

- **WHEN** Telegram 将已成功处理过的 update 再次投递
- **THEN** 系统直接确认成功，不再次转发该消息

#### Scenario: 同一 update 并发到达只处理一次

- **WHEN** 同一个 `update_id` 的两个请求同时到达且都尚未完成处理
- **THEN** 只有一个请求执行转发等副作用，另一个不产生重复转发

#### Scenario: 处理中断后仍可重投

- **WHEN** 某个 update 取得处理权后处理失败或中断，Telegram 随后重投同一 `update_id`
- **THEN** 该 update 可被重新处理，消息最终送达，不因先前的中断而被永久跳过

### Requirement: 用户消息限流

非管理员用户的私聊消息 MUST 受频率限制；超限消息不被转发，且提示语在短时间窗口内 MUST 只发送一次（防抖）。

限流额度 MUST 按用户发送的消息计量，MUST NOT 按投递次数计量：同一 `update_id` 的重投 MUST NOT 再次消耗限流额度。此前因处理未完成而被请求重投的消息，MUST NOT 在重投时因限流而被丢弃。

#### Scenario: 高频消息被限流

- **WHEN** 用户在 2 秒内发送超过限额条数的消息
- **THEN** 超限消息不被转发，用户收到一次"请求过于频繁"提示

#### Scenario: 重投不重复消耗限流额度

- **WHEN** 一条消息因处理未完成返回重投请求，Telegram 在同一限流窗口内重投同一 `update_id`
- **THEN** 该重投不被限流拦截，消息按正常流程处理并送达

### Requirement: 专属话题创建

已验证用户的首条中继消息 MUST 触发在管理群创建该用户的专属论坛话题，话题名包含用户名称与数字 ID；同一用户并发到达的多条消息 MUST 只产生一个话题，且不得通过锁轮询等待实现。

话题创建占位 MUST 具备所有权标识：持有者写入话题映射时 MUST 校验自身仍为当前占位持有者，占位过期并被他人接管后，原持有者 MUST NOT 覆盖已经写入的话题映射。因占位被他人持有而未能建立话题的消息 MUST 请求重投，MUST NOT 以成功状态结束。

#### Scenario: 首条消息创建话题

- **WHEN** 已验证且无话题映射的用户发送第一条消息
- **THEN** 管理群出现一个以"名称 | ID"命名的新话题，且该消息被转发到此话题

#### Scenario: 并发消息不重复建话题

- **WHEN** 同一用户的多条消息在同一时刻到达
- **THEN** 管理群只创建一个话题，所有消息都转发到该话题

#### Scenario: 过期持有者不得覆盖新映射

- **WHEN** 某次话题创建请求超时导致占位被接管，新的持有者已经创建话题并写入映射，随后原请求才返回其创建结果
- **THEN** 当前生效的话题映射保持为新持有者创建的话题，用户后续消息全部进入该话题

### Requirement: 消息转发与送达标记

已验证且未屏蔽用户的消息 MUST 被转发到其专属话题；转发成功后系统 MUST 给用户的原消息添加已送达表情回应。

用户消息 MUST NOT 出现"未送达管理群、未提示用户、且不会被重投"的三重静默结局：转发因话题失效或临时故障未能完成时，系统 MUST 请求重投；仅当失败为明确的永久性错误时，MUST 以用户或管理员可见的提示结束处理。

#### Scenario: 文本消息转发并标记

- **WHEN** 已验证用户发送一条文本消息
- **THEN** 消息出现在其专属话题中，且用户侧原消息获得 👍 表情回应

#### Scenario: 临时故障不得静默丢弃

- **WHEN** 转发与降级复制均因 Telegram 限流、5xx 或网络异常而失败
- **THEN** 本次处理请求重投，不给出已送达标记，消息在重投后仍有机会送达

### Requirement: 管理员回复转达

管理员在用户专属话题内发送的消息 MUST 被复制发送给对应用户。

发送失败 MUST 按性质区分处理：目标用户已停用机器人等永久性失败 MUST 在话题内提示失败并结束处理；限流、5xx 与网络异常等临时性失败 MUST 请求重投，MUST NOT 以成功状态确认，避免管理员回复永久丢失。

#### Scenario: 话题内回复送达用户

- **WHEN** 管理员在某用户的话题内发送消息
- **THEN** 该用户在私聊中收到这条消息

#### Scenario: 用户已停用机器人

- **WHEN** 管理员回复的目标用户已 block 机器人
- **THEN** 话题内出现发送失败提示，系统不崩溃，不再重复投递

#### Scenario: 临时失败请求重投

- **WHEN** 管理员回复因 Telegram 限流或 5xx 失败
- **THEN** 本次处理请求重投，该回复在重投后送达用户

### Requirement: 话题失效恢复

用户专属话题不可用时系统 MUST 自动恢复，不得陷入持续静默失败：话题已被删除（thread not found 类错误）时清除失效映射并在该用户下次消息时重新创建话题；话题被关闭（TOPIC_CLOSED 错误）时 MUST 先尝试自动重新打开话题并重试发送，仅当重开失败且失败原因为永久性错误（如权限不足、话题不存在）时才按删除处理。限流、5xx、网络异常等临时性错误 MUST NOT 触发映射清除，MUST 请求重投。

清除失效映射 MUST 是条件操作，仅当当前映射仍为本次失败所针对的话题时才执行；针对已被替换的旧话题的迟到错误 MUST NOT 清除新的话题映射。

触发话题重建的那条用户消息本身 MUST NOT 丢失：当转发因话题失效而失败、系统清除映射后，该次处理 MUST 请求 Telegram 稍后重投，使该消息在重投时经由新建话题送达管理群。

#### Scenario: 话题被管理员删除

- **WHEN** 用户话题已被删除，该用户又发来消息
- **THEN** 系统清除旧映射，为该用户创建新话题并完成转发（允许提示用户重发一次）

#### Scenario: 触发重建的消息不得丢失

- **WHEN** 用户话题已被删除，该用户发来一条消息导致转发失败并清除映射
- **THEN** 本次处理请求 Telegram 重投，重投时该消息经新建话题成功送达管理群，用户最终获得已送达标记

#### Scenario: 话题被管理员关闭

- **WHEN** 用户话题被关闭，该用户又发来消息
- **THEN** 系统自动重新打开该话题并完成转发，对话历史保留

#### Scenario: 重开临时失败不清映射

- **WHEN** 话题被关闭且重新打开操作因限流、5xx 或网络异常失败
- **THEN** 话题映射保持不变，本次处理请求重投，系统不创建新话题

#### Scenario: 临时错误不清映射

- **WHEN** 转发因 Telegram 限流暂时失败
- **THEN** 话题映射保持不变，不触发重建

#### Scenario: 旧话题的迟到错误不清新映射

- **WHEN** 针对某个已被替换的旧话题的失效错误在新话题映射写入之后才返回
- **THEN** 新话题映射保持有效，管理员在新话题中的回复仍能定位到该用户

### Requirement: 置顶资料卡

新话题创建时系统 MUST 向话题发送用户资料卡（名称、ID、时间、备注）并置顶；资料卡 MUST 携带屏蔽/解封与备注操作按钮。

首次发送的资料卡 MUST 已经包含这些操作按钮，MUST NOT 依赖后续的刷新操作才使按钮可用。

#### Scenario: 新话题带置顶资料卡

- **WHEN** 用户专属话题被创建
- **THEN** 话题顶部有置顶的资料卡，含用户名称、ID 与操作按钮

#### Scenario: 首张资料卡即可屏蔽用户

- **WHEN** 管理员在用户话题创建后立即查看置顶资料卡，且此前未发生任何备注或屏蔽操作
- **THEN** 资料卡上存在可点击的屏蔽按钮，点击后该用户被屏蔽

### Requirement: 编辑消息通知

用户编辑已发送的私聊消息时，系统 MUST 在其专属话题内发送包含新内容的编辑提示。

编辑消息 MUST 与新消息适用同一套准入策略：编辑内容进入管理群前 MUST 校验用户当前验证状态与屏蔽状态，并 MUST 应用屏蔽关键字与消息类型过滤。不满足准入条件的编辑 MUST NOT 被转达到管理群。

#### Scenario: 用户编辑消息

- **WHEN** 已有话题且已验证的用户编辑了此前发送的消息
- **THEN** 话题内出现"用户修改了消息"提示及新文本

#### Scenario: 未验证用户的编辑不进入管理群

- **WHEN** 用户被管理员重置为未验证状态后，编辑一条此前发送的私聊消息
- **THEN** 编辑内容不被转达到管理群，用户收到验证引导

#### Scenario: 编辑内容受关键字过滤约束

- **WHEN** 用户把一条已发送消息编辑为包含屏蔽关键字的内容
- **THEN** 编辑内容不被转达到管理群，并按屏蔽关键字策略处理
